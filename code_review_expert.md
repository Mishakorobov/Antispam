# Архитектурный аудит и анализ рисков системы AntiSpam

Данный документ содержит глубокий технический анализ текущей реализации системы блокировки спам-пулов (связка **FastAPI + SQLite-WAL** на сервере и **Kotlin + Room + CallScreeningService** на Android). В документе выделены векторы атак, алгоритмические и инфраструктурные ограничители, продуктовые «точки боли» пользователей и дорожная карта масштабирования.

---

## 1. Потенциальные уязвимости (Security & Anti-Abuse)

### 1.1. Sybil-атака и спуфинг `device_hash` (Отравление базы / Data Poisoning)
* **Суть проблемы:** В текущей архитектуре дедупликация голосов опирается на `device_hash` (лимит 1 голос за «сотню» в 24 часа). Поскольку API публично (`POST /api/v1/report`), злоумышленник или конкурент может написать простой скрипт, генерирующий 3–5 случайных `device_hash` и отправляющий жалобы на соседние номера из одного диапазона (`7XXXXXXXX01`, `7XXXXXXXX02`, `7XXXXXXXX03`). Это позволит принудительно заблокировать чужой бизнес, колл-центр клиники или регионального оператора у всех пользователей приложения.
* **Решение:**
  1. **Внедрение Google Play Integrity API:** Клиентское приложение при отправке батча жалоб запрашивает криптографический токен у сервисов Google, подтверждающий, что запрос идет с реального нерутованного Android-устройства и оригинальной сборки APK.
  2. **Система репутации устройств (Trust Score):** Новые `device_hash` получают вес голоса $w = 0.2$. Вес растет до $1.0$ только после нескольких недель активности и совпадения их жалоб с жалобами других подтвержденных пользователей.
  3. **Rate Limiting по IP / подсетям (ASN):** Ограничение числа засчитываемых голосов для одного пула с одной IP-подсети `/24` (для IPv4) или `/48` (для IPv6).

### 1.2. Коллизия пулов с номерами MNP (Перенесенные номера)
* **Суть проблемы:** Реестр Минцифры (`ABC/DEF`) отражает **первичное** выделение диапазонов операторам по тысячам и десяткам тысяч. Однако абоненты активно переносят номера между операторами (MNP). Если колл-центр выкупил остатки «сотни» у виртуальной АТС, но внутри этой же «сотни» 3 года назад обычный человек перенес свой номер `79991234567` в другого оператора — блокировка всей сотни `[79991234500, 79991234599]` отрежет этого абонента от звонков пользователям приложения.
* **Решение:**
  1. **Разделение логики для ABC (географические: 495, 499, 812 и др.) и DEF (мобильные: 9xx):** В кодах ABC перенос номера практически не используется физлицами, там блокировка целыми сотнями и тысячами безопасна. В кодах DEF блокировать всю сотню можно только при высоком пороге ($\ge 7\text{–}10$ уникальных номеров внутри сотни), а при малом числе жалоб — блокировать точечно конкретные номера, пока не накопится критическая масса.
  2. **Механизм автоматической амнистии номера:** Если пользователи приложения сами совершают *исходящие* вызовы на номер внутри заблокированного пула или добавляют его в контакты — отправлять анонимизированный сигнал `false_positive` для исключения конкретного номера из диапазона.

### 1.3. Игнорирование статуса верификации номера (Caller ID Spoofing)
* **Суть проблемы:** Нелегальные спамеры могут подменять Caller ID на номера из обычных абонентских пулов. Жалобы пользователей на подмененные номера приведут к блокировке ни в чем не повинных владельцев этих номеров.
* **Решение:**
  * Начиная с Android 11 (API 30) в `Call.Details` доступно свойство `callerNumberVerificationStatus`. В России работает система «Антифрод» (единая платформа верификации вызовов ЕПВВ). Если оператор пометил вызов как неверифицированный (`VERIFICATION_STATUS_FAILED`), такой звонок нужно блокировать мгновенно, но **не отправлять** его номер в серверную кластеризацию пулов, чтобы не загрязнять статистику подменными номерами.

## 2. Узкие горлышки (Ограничители производительности и архитектуры)

### 2.1. Конкурентная запись в SQLite-WAL на бэкенде и ETL-блокировки
* **Суть проблемы:** SQLite даже в режиме `WAL` (Write-Ahead Logging) поддерживает только **одну транзакцию на запись** в единицу времени (`database is locked`). Когда раз в неделю запускается ETL-процесс (`downloader.py` / `parser.py`), обновляющий сотни тысяч строк в `registry_ranges`, или отрабатывает тяжелый пересчет в `clustering.py`, входящие запросы `POST /api/v1/report` начнут выпадать по таймауту (`SQLITE_BUSY`).
* **Решение:**
  1. **Shadow Table Swap для ETL:** Парсер реестра Минцифры должен загружать данные во временную таблицу `registry_ranges_staging` батчами, а в конце делать мгновенный атомарный `DROP TABLE` / `ALTER TABLE RENAME` за $< 5\text{ мс}$.
  2. **In-Memory буферизация жалоб:** Принимать `POST /api/v1/report` в асинхронную очередь в памяти (`asyncio.Queue` или Redis) и сбрасывать в SQLite одним батч-инсертом раз в 5–10 секунд через фоновый корутин-воркер.
  3. При росте аудитории свыше $50\,000\text{ DAU}$ — плавный переход на PostgreSQL (благодаря SQLAlchemy это потребует лишь смены `DATABASE_URL` и адаптации пары индексов).

### 2.2. Деградация `BETWEEN` в SQLite на клиенте при росте базы диапазонов
* **Суть проблемы:** Запрос `WHERE :num BETWEEN range_start AND range_end` по стандартному B-Tree индексу `(range_start, range_end)` работает нестабильно по времени! SQLite использует индекс для поиска всех записей, где `range_start <= :num`, а затем **линейно сканирует** индекс для проверки `range_end >= :num`. Если в базе 50 000 диапазонов, для номера с кодом `7999...` SQLite просканирует почти все 50 000 индексных записей от `7300...` до `7999...`, что нарушит ваш жесткий SLA $< 15\text{ мс}$ на слабых бюджетных процессорах.
* **Решение (Критический оптимизационный шаг):**
  Поскольку диапазоны в `active_blocks` **не пересекаются** (или могут быть слиты при сохранении), запрос в Room DAO необходимо переписать с использованием `ORDER BY range_start DESC LIMIT 1`:
  ```sql
  SELECT 1 FROM blocked_pools 
  WHERE range_start <= :num 
  ORDER BY range_start DESC 
  LIMIT 1
  -- и уже для этой единственной строки проверить range_end >= :num:
  ```
  Или в виде подзапроса за $O(\log N)$ (ровно 1 чтение листа B-дерева, $< 0.2\text{ мс}$ при любом размере базы):
  ```sql
  SELECT 1 FROM (
      SELECT range_end FROM blocked_pools 
      WHERE range_start <= :num 
      ORDER BY range_start DESC LIMIT 1
  ) WHERE range_end >= :num;
  ```

### 2.3. Убийство фоновых процессов агрессивными OEM-оболочками (Xiaomi, Huawei, Samsung)
* **Суть проблемы:** Ограничение `BatteryNotLow` в `SyncPoolsWorker` и фоновый `PhoneStateReceiver` для Post-Call уведомлений часто блокируются проприетарными контроллерами питания (MIUI/HyperOS Battery Saver, Samsung Sleeping Apps). В итоге у пользователя перестает обновляться база пулов и перестают всплывать окна репорта после коротких звонков.
* **Решение:**
  1. **Оппортунистическая синхронизация при открытии UI и при срабатывании `CallScreeningService`:** Поскольку `CallScreeningService` гарантированно будится самой системой Android при каждом звонке (даже если приложение в глубоком сне), внутри `onScreenCall` после отправки ответа `respondToCall()` можно проверить timestamp последней синхронизации и при устаревании базы $> 24$ часов запустить легкий `OneTimeWorkRequest` с `Expedited` приоритетом.
  2. **Экран онбординга OEM-разрешений:** Внедрить проверку `PowerManager.isIgnoringBatteryOptimizations` и плашку в настройках с переходом в системное меню «Без ограничений» для китайских прошивок.

### 2.4. «Раздувание» версионности при синхронизации дельт (`GET /api/v1/pools?since={version}`)
* **Суть проблемы:** Если клиент не выходил в сеть 2 месяца, а за это время на сервере тысячи пулов добавились и удалились по TTL, инкрементальная история изменений может оказаться больше, чем вся текущая база целиком. Кроме того, при `since={version}` клиенту нужно передавать не только новые блокировки (`UPSERT`), но и **удаленные по TTL диапазоны (`TOMBSTONES`)**, иначе у клиента в Room навсегда останутся протухшие 30-дневные блокировки.
* **Решение:**
  1. Добавить таблицу `deleted_blocks_log (range_start, range_end, deleted_at_version)` или хранить в `active_blocks` флаг `is_active: bool`, чтобы дельта возвращала массивы `added` и `removed`.
  2. Если разрыв версий `server_version - client_version > 5000`, сервер возвращает флаг `"full_reset": true` и полный компактный слепок активных пулов, а клиент делает `DELETE FROM blocked_pools` и вставляет чистый срез в одной транзакции.

## 3. Продуктовые «точки боли» (UX & Customer Pain Points)

### 3.1. Блокировка курьеров, такси и доставки (Call Masking / SIP Proxy)
* **Суть проблемы:** Сервисы доставки (Яндекс Доставка, Ozon, Купер, CDEK) и агрегаторы такси используют временные подменные SIP-номера из пулов тех же самых B2B-операторов (МТТ, Телфин, Билайн Бизнес), что и телефонные опросы. Если заблокировать весь пул B2B-оператора целиком, до пользователя не дозвонится курьер с заказом.
* **Решение:**
  1. **Временная кнопка «Жду курьера / доставку» (Пауза на 2 часа):** На главном экране (рядом с Hero Shield виджетом) добавить быструю кнопку или тайл в шторке уведомлений (Quick Settings Tile), который временно переводит жесткий сброс (`REJECT`) в режим «Тихий звонок» (`setSilenceCall(true)` без сброса) на 1–2 часа.
  2. **Категоризация пулов по длительности разговоров:** У опросов/спама 95% звонков длятся $< 15$ сек, но идут веером по разным регионам. У курьерских прокси-пулов средняя длительность звонка составляет $20\text{–}45$ секунд. Передавать в репорте не только факт короткого звонка, но и точный `duration_sec`.

### 3.2. Попадание Post-Call уведомления на легитимные короткие звонки
* **Суть проблемы:** `PhoneStateReceiver` ловит любой звонок длительностью $< 30$ секунд и показывает пуш-уведомление с предложением заблокировать номер. Если пользователю позвонил знакомый, не записанный в контакты, или курьер («Я у подъезда, выходите» — разговор длится 7 секунд), постоянные навязчивые уведомления начнут вызывать раздражение (Notification Fatigue), или пользователь случайно нажмет «Блок» не глядя.
* **Решение:**
  1. **Умный фильтр в `PhoneStateReceiver`:** Не показывать Post-Call пуш, если:
     * Звонок был **исходящим** или этому номеру пользователь сам звонил за последние 30 дней.
     * Номер уже принадлежит оператору из `Server Whitelist`.
  2. **Авто-скрытие уведомления (Timeout):** Настроить `NotificationCompat.Builder.setTimeoutAfter(60_000)` — если пользователь не нажал кнопку «Спам» в течение 1 минуты после звонка, уведомление тихо исчезает из шторки само.
  3. **Undo-действия:** При нажатии «Блок» в пуше показывать на 5 секунд снэкбар или обновлять пуш кнопкой «Отменить», прежде чем отправлять репорт в очередь `WorkManager`.

### 3.3. Отсутствие прозрачности (Страх пропустить важный звонок)
* **Суть проблемы:** Когда `AntiSpamCallScreeningService` молча сбрасывает звонок (`setSkipNotification(true)`), тревожные пользователи начинают переживать, не заблокировало ли приложение звонок из поликлиники или банка.
* **Решение:**
  * В журнале вызовов внутри приложения (`ui/calllog`) рядом с каждым заблокированным номером выводить понятное объяснение из базы: *«Заблокирован по пулу: АО "МТТ" (Виртуальная АТС), жалоб на сотню: 14, категория: Опросы / ВЦИОМ»*. Это формирует абсолютное доверие к алгоритму.

## 4. Точки развития и масштабирования (Product Roadmap)

### 4.1. Интеграция с Android 14/15 Call Screening & In-Call Overlay
* **Куда развивать:** Помимо полного сброса (`REJECT`), добавить второй уровень срабатывания для «подозрительных» пулов (где пока набралось только 1–2 жалобы вместо 3).
* **Как работает:** Для пулов со средним `confidence_score` звонок не сбрасывается, но приложению выводится аккуратная плашка поверх экрана вызова (или системный бейдж Caller ID): `⚠️ Подозрение на опрос (Пул: Манго Телеком)`, либо автоматически выключается звук рингтона (`setSilenceCall(true)`), оставляя пользователю право самому решить — брать трубку или нет.

### 4.2. Классификация по временным паттернам (Velocity-детектор на бэкенде)
* **Куда развивать:** ВЦИОМ и крупные колл-центры запускают автодозвон (Predictive Dialer) волнами. Когда они подключают свежий пул номеров, первые 2 пользователя, которым они позвонят, еще не защищены (порог в 3 жалобы еще не пробит).
* **Как работает:** Снижать порог блокировки с 3 до **2 жалоб**, если они поступили в интервале **менее 15 минут** из разных регионов РФ на один и тот же `bucket_100`. Обычные люди не получают звонки из одной «сотни» виртуальной АТС с разницей в 5 минут в разных концах страны.

### 4.3. Сжатые бинарные фильтры (Roaring Bitmaps / Range Tree)
* **Куда развивать:** Если приложение масштабируется на сотни тысяч пользователей и база вырастет до 100 000+ микро-пулов.
* **Как работает:** Вместо передачи JSON-массивов по REST API, отдавать клиенту бинарный дамп (или Protobuf / FlatBuffers), что сократит размер ответа в $5\text{–}8$ раз и ускорит парсинг на клиенте без нагрузки на Garbage Collector в Kotlin.

### 4.4. Быстрый экспорт для iOS (`CXCallDirectoryExtension`)
* **Куда развивать:** У вас уже готов весь аналитический бэкенд и дизайн-система в стиле Apple HIG.
* **Как работает:** Добавить на бэкенде эндпоинт генерации отсортированного массива 64-битных чисел для самых активных спам-сотен, что позволит за 1–2 недели выпустить iOS-версию приложения, использующую ту же самую облачную базу.
